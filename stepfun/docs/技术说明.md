# 技术说明：端侧向量化 + seekdb 混合检索迷你知识库

作者：FDE WorkMate

测试环境：Apple M4（10 核）、macOS 27.0.1、Chrome 156（Playwright 驱动本机 Chrome，WebGPU 适配器 apple/metal-3）、Node 24.1、seekdb-js 1.4.0 嵌入式（seekdb-v1.4.0.0）。数据集 mmarco-zh-mini：2000 段，分批次 1（1500 段）和批次 2（500 段），100 条带标注查询，Top-K=10。下文数字都来自 `bench/summary.md`，原始数据在 `bench/results/`。每个配置跑 1 次冷启动和 2 次热启动，取中位数。

## 1. 模型与量化

- 模型：`BAAI/bge-small-zh-v1.5`（MIT，512 维，CLS 池化 + L2 归一化）。ONNX 导出版本为 `Xenova/bge-small-zh-v1.5`，revision `75c43b069aac4d136ba6bc1122f995fedcfd2781`。只下载 FP32 原始文件，量化全部由 `scripts/prepare_model.py` 在本地完成，sha256 记录在 `models/manifest.json`。
- 量化方案：
  - FP16：`onnxruntime.transformers.float16`，`keep_io_types=True`。
  - INT8 动态量化：`quantize_dynamic`，MatMul、Gemm 和词向量 Gather 的权重做 per-channel 对称 QInt8，激活在运行时量化。
  - WQ8（INT8 权重量化）：MatMul 转成 `MatMulNBits(bits=8, block=32)`，Gather 用 QInt8，激活保持浮点。这个方案专门为 WebGPU 准备：动态量化的 `DynamicQuantizeLinear`/`MatMulInteger` 在 WebGPU 上会回退到 CPU 执行，实测吞吐只有 37.5 段/s。
- 质量评测方法：同一份语料和查询，用 seekdb 精确向量检索（`approximate=false`）计算指标，排除 HNSW 近似误差的干扰。

| 精度 | 文件体积 | 压缩比 | 精确检索 nDCG@10 | Recall@10 | 相对 FP32 |
|---|---|---|---|---|---|
| FP32（基线） | 90.5 MB | 1.00× | 0.7819 | 0.870 | — |
| FP16 | 45.3 MB | 2.00× | 0.7816 | 0.870 | −0.04% |
| WQ8 | 24.3 MB | 3.72× | 0.7739 | 0.870 | −1.0% |
| INT8 动态 | 22.9 MB | 3.95× | 0.7554 | 0.870 | −3.4% |

## 2. 端侧运行

- 运行时：Transformers.js 4.3.1 + ONNX Runtime Web，在 Web Worker 中推理。模型、tokenizer 和 ORT wasm 都从本地服务同源加载（`env.allowRemoteModels=false`）。e2e 测试断言页面没有发出任何对外请求。
- 后端选择：依次检测 `navigator.gpu`、`requestAdapter()` 和 `requestDevice()`，都通过后显式使用 `device:"webgpu"`。任何一步失败，或者 WebGPU 会话创建失败，都会自动改用 `device:"wasm"`（多线程 SIMD，页面开启 COOP/COEP 跨源隔离）。页面右上角显示当前后端，降级时同时显示原因。默认精度在 WebGPU 下为 FP16，在 WASM 下为 INT8。
- 降级验证：`scripts/e2e.mjs` 在两种环境下跑完整流程。正常 Chrome 中显示「WebGPU · fp16」。`--disable-gpu` 启动时显示「WASM（CPU）· int8」，降级原因为「requestAdapter() 返回 null」，导入、检索、增量和会话恢复都通过。截图见 `docs/e2e-*.png`。

## 3. seekdb 使用

- 存储结构：每个知识库对应一个 collection，物理表包含 `_id`、`document`、`embedding VECTOR(512)` 和 `metadata JSON`（doc_id、chunk、title、batch）。索引有两个：`VECTOR KEY ... HNSW, DISTANCE=COSINE, SYNC_MODE=ASYNC` 和 `FULLTEXT KEY ... WITH PARSER ik`。状态存在三张普通表里：`kb_registry` 记录知识库、维度、模型签名和已刷新批次，`kb_batches` 记录导入批次的状态和耗时，`kb_sessions` 记录会话。
- 混合检索：调用 `collection.hybridSearch`，由 `DBMS_HYBRID_SEARCH` 生成 SQL。生成的 SQL 把全文 `MATCH ... AGAINST` 和向量 `APPROXIMATE LIMIT` 两路结果做 full join，再在库内计算 RRF 分数并排序，客户端不拼合两路结果。页面勾选「显示 SQL」可以查看。RRF 参数由网格实验确定（`bench/tuning/`）：k=10、窗口为 2×TopK。和 SDK 默认值（k=60、窗口 40）相比，混合检索 nDCG@10 从 0.674 提高到 0.723，Recall@10 从 0.857 提高到 0.917。分词器对比时 ik 最好，ngram、ngram2 次之。beng 对中文几乎没有召回（全文 Recall@10 只有 0.05）。
- 写入与刷新：每个导入批次先多次批量写入，最后调用一次 `refresh_index()`。之后用探针 chunk 的自身向量做 KNN 校验可见性，校验通过才把批次标为 `refreshed`。增量验证用了 30 条正例只在批次 2 中的查询：批次 2 导入前 Recall@10 为 0.000，刷新后为 0.933。

## 4. 状态与优化

- 一致性：知识库绑定「模型@revision:精度」签名，写入和检索时签名不一致返回 409。切换知识库时前端自动加载对应精度的模型。chunk id 由 `docId#序号` 组成，docId 由内容哈希生成，重复导入是幂等的。同一知识库的写操作串行执行。刷新页面后，会话从 `kb_sessions` 恢复。
- 优化项：推理批大小 32；按文本长度排序后分批，减少 padding；推理与上一组写入流水并行；用一条多行 INSERT 代替 SDK 逐行 upsert（SDK 每行要 get 一次再 insert）；每批只刷新一次；查询向量化的预热单独计时；模型通过 HTTP 缓存和 Cache API 实现热加载。

| 配置（2000 段导入 + 100 查询） | 向量化吞吐 | 导入总耗时 | seekdb 检索（中位/p95） | 端到端查询（中位/p95） | 冷加载 / 热加载 | 混合 nDCG@10 |
|---|---|---|---|---|---|---|
| 优化前基线 FP32 + WebGPU | 93.9 段/s | 77.4 s | 3.2 / 4.9 ms | 12.5 / 18.3 ms | 876 / 283 ms | 0.738 |
| FP16 + WebGPU | 396.6 段/s | 7.8 s | 3.3 / 4.9 ms | 12.7 / 19.4 ms | 571 / 204 ms | 0.726 |
| WQ8 + WebGPU | 213.2 段/s | 12.8 s | 3.3 / 4.9 ms | 13.3 / 20.1 ms | 595 / 224 ms | 0.724 |
| 优化前基线 FP32 + WASM | 55.7 段/s | 95.1 s | 8.5 / 13.0 ms | 17.4 / 23.8 ms | 609 / 267 ms | 0.736 |
| INT8 + WASM | 41.5 段/s | 50.4 s | 9.5 / 18.4 ms | 20.8 / 33.1 ms | 540 / 214 ms | 0.717 |
| WQ8 + WASM | 47.9 段/s | 43.6 s | 8.9 / 16.1 ms | 23.8 / 32.6 ms | 872 / 187 ms | 0.737 |

- 单项消融：在 FP16 + WebGPU 上每次只去掉一项优化，导入总耗时从 7.8 s 变为：逐条推理 16.2 s，不按长度排序 15.4 s，SDK 逐行 upsert 12.9 s，每 16 条刷新一次 51.8 s。频繁刷新代价最大：批次 1 的刷新耗时从 0.4 s 增加到 31.7 s。
- 首次与后续请求：模型加载后第一次查询的端到端耗时为 24–59 ms，预热后中位数为 12.7 ms。冷加载时 FP32 取文件要 842 ms，FP16 只要 169 ms。
- 局限：
  - 混合检索 nDCG 的波动范围约 ±0.01。原因是 HNSW 每次重建，近似召回结果不完全相同。
  - WASM 配置下，浏览器推理线程和嵌入式 seekdb 抢同一组 CPU，所以服务端写入耗时会明显变长。

## 已知问题与规避（seekdb-js 1.4.0 嵌入式，均有复现记录）

1. 以 `[` 开头的字符串参数会被当作向量字面量直接拼进 SQL，导致写入失败（`Parse error`）。语料中有 3 段正文触发了这个问题。规避方法：服务端对自由文本的首个 `[` 做全角替换，并限制 id 不能以 `[` 开头。测试用例覆盖了这种情况。
2. 新实例中第一个 HNSW collection 偶尔一直无法被近似检索，而且 refresh 会超时。规避方法：服务启动时用临时 collection 做一次向量索引自检，再对外提供服务。
3. HNSW 是异步构建的，写入后不调用 `refresh_index()` 就无法被检索到。我们只用 refresh 后的可见性校验结果来判定批次状态。
